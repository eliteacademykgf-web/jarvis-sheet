# jarvis-sheet

Данные для таблицы сквозной аналитики: CRM-метрики за день из AmoCRM
и статистика объявлений по дням из Meta Marketing API.
Пишет сырые данные в Google Sheets (листы `meta_daily` и `crm_daily`) и собирает из них лист «Сквозная аналитика <Месяц>».
Обновляет таблицу раз в час (`run_hourly.py`), о сбоях пишет в Telegram.
Основной вариант — офисный ПК заказчика (`run_loop.py`, инструкция —
[OFFICE-PC.md](OFFICE-PC.md)); запасной — крон Railway (раздел ниже).

## Файлы

- `config.py`: переменные окружения (`AMO_DOMAIN`, `AMO_TOKEN`, `META_TOKEN`, `AD_ACCOUNT_ID`, `SPREADSHEET_ID`, `GOOGLE_SERVICE_ACCOUNT_JSON`, `ALERT_BOT_TOKEN`, `ALERT_CHAT_IDS`).
- `amo_client.py`: запросы к AmoCRM. Перенесено из `jarvis-amo/main.py`; отличие — ошибки API не глотаются (`AmoAPIError`), см. ниже.
- `run_hourly.py`: часовое обновление — вчера и сегодня; при сбое уведомление и код выхода 1.
- `alerts.py`: уведомление о сбое в Telegram (токены вырезаются из текста).
- `run_loop.py`: цикл для офисного ПК — `git pull` и `run_hourly.py` при старте
  и каждый час в :05, каждый раз новым процессом; если обновился сам цикл —
  выход с кодом 3 и перезапуск из `start-sheet.bat`; второй экземпляр не
  стартует; лог в `logs/`.
- `start-sheet.bat`, `install-autostart.bat`, `uninstall-autostart.bat`,
  `update-sheet.bat`: запуск, автозапуск и обновление на офисном ПК (Windows,
  без прав администратора). Только ASCII и CRLF (`.gitattributes`).
- `railway.json`: крон Railway `5 * * * *` (каждый час в :05 UTC).
- `tests/`: тесты без сети (`pytest`).
- `metrics.py`: `compute_breakdown(df, dt)` — итог CRM за период и он же по кодовым словам за один проход; `compute_daily_metrics(date)` — только итог дня.
- `build_daily_source.py`: `build_meta_rows(date)` (строка на объявление, Meta) и `build_crm(date)` (сводка CRM на день + строки по кодовым словам). Склейка — на уровне листа месяца.
- `sheets_client.py`: подключение к Google Sheets и upsert на листы `meta_daily`, `crm_daily`, `crm_by_code`.
- `sheet_builder.py`: `rebuild_month_sheet(year, month)`, пересборка листа месяца одним `batchUpdate`.
- `write_to_sheets.py`: запись дня или диапазона дней (по умолчанию вчера) в таблицу и пересборка листа месяца.
- `verify.py`: один день (по умолчанию вчера): Meta по объявлениям и CRM одной сводкой, друг под другом. С `--month` выводит суммы за прошлый календарный месяц для сверки с ботом.
- `meta_client.py`: `get_daily_ad_stats(ad_account_id, date, access_token)`, строки объявление × день.
- `verify_meta.py`: последние 7 полных дней из Meta для ручной сверки с Ads Manager.

## Запуск локально

```bash
cd jarvis-sheet
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env    # заполнить AMO_* и META_TOKEN / AD_ACCOUNT_ID
python verify.py              # вчера: Meta по объявлениям + CRM за день
python verify.py 2026-09-20   # конкретный день
python verify.py --month      # сверка месяца с ботом
python verify_meta.py
python write_to_sheets.py              # вчера → Google Sheets
python write_to_sheets.py 2026-09-20   # конкретный день
python write_to_sheets.py 2026-09-01 2026-09-23   # дозаливка диапазона
python sheet_builder.py 2026-09        # только пересобрать лист месяца
python run_hourly.py                   # то же, что делает крон: вчера + сегодня
pip install -r requirements-dev.txt && python -m pytest   # тесты
```

Можно без `.env`: переменные окружения тоже подхватываются
(`AMO_DOMAIN=... AMO_TOKEN=... python verify.py`).

## Как считаются показатели

- Этапы накопительные («дошёл до этапа или дальше») по `sort` статусов воронки.
  Открытые лиды оцениваются по текущему статусу. У закрытых (142/143) берётся
  максимум по истории `lead_status_changed`. 143 при этом не учитывается,
  142 считается дальше всех этапов.
- Когорта: лиды, созданные в этот день в «Отделе продаж», после `dedup_leads`.
- Продажи и выручка: события перехода в 142 или «получена предоплата».
  Продажа засчитывается один раз, в день ПЕРВОГО такого события за всю историю
  сделки (предоплата 3-го и 142 20-го — продажа 3-го). Бот считает иначе:
  у него такая сделка — продажа в обоих периодах. Выручка — сумма `price`.
- Сумма этапов по дням может быть чуть больше расчёта за месяц одним
  периодом: дедупликация по контакту/телефону работает внутри дня.

## Ошибки API

- AmoCRM: сеть, 429 и 5xx повторяются 4 раза (пауза 3, 6, 12 с, либо
  `Retry-After`), 401 и прочие 4xx — сразу `AmoAPIError`. Раньше (как в боте)
  ошибка превращалась в пустой ответ, и в таблицу ушли бы нули или
  неполные цифры.
- Meta: `MetaAPIError`, см. раздел Meta.
- День собирается целиком (Meta и CRM) и только потом пишется: день, на
  котором упал API, в таблице остаётся прежним.

## Разбивка по кодовому слову

Сделка связывается с объявлением только через кодовое слово: поле контакта
«Кодовое слово» в AmoCRM (`FIELD_CODE_WORD` = 1145111) ↔ `code_word` объявления
на листе `ads_manual`.

- Слова сравниваются без учёта регистра и лишних пробелов, но **с эмодзи**:
  «ИТАЛИЯ 💚» и «ИТАЛИЯ 🌟» — разные объявления (`metrics.code_key`).
- Лист `crm_by_code`: день × кодовое слово, `code_key` "" — заявки без слова.
  День заменяется целиком: слова, пропавшие из дня, обнуляются.
- Лист месяца: если в дне есть заявки со словом, объявления группируются по
  коду из `ads_manual`, у группы — CRM-цифры её слова (объединены по высоте
  группы), цены — расход группы / показатель. Заявки без слова и со словами,
  которых нет ни у одного объявления дня, — отдельной строкой в конце блока.
  Итог дня — сумма блока, совпадает с `crm_daily`.
- Если заявок со словом в дне нет, блок как раньше: CRM одним числом на день.
- Колонка `note` на `crm_daily`: «С кодовым словом: X из Y заявок» — видно,
  заполняют ли поле в CRM.
- На 25.09.2026 поле пустое у всех сделок: разбивка заработает сама с того
  дня, как его начнут заполнять (менеджер или ИИ-бот). Задним числом — нет.

## Нагрузка на API

История переходов запрашивается через `/events` с `filter[entity_id]`,
по 10 лидов за запрос (больше AmoCRM не принимает). При ~130 сделках в день
это ~13 запросов на историю плюс лиды, контакты и события продаж.

## Meta

- Graph API v26.0. Запрос `/act_{id}/insights` с `level=ad`, `time_increment=1`,
  пагинация по `paging.next` до конца.
- Дни в часовом поясе рекламного аккаунта (сейчас Europe/Moscow, UTC+3),
  а CRM считает по Бишкеку (UTC+6). С 00:00 до 03:00 по Бишкеку «сегодня»
  для аккаунта ещё не наступило — такой день Meta не запрашивается
  (`get_account_today`), строк объявлений за него пока нет.
- Токен передаётся заголовком `Authorization` и в URL не попадает. Все тексты
  ошибок и логов маскируются (`access_token=***`).
- Ошибка Meta поднимает `MetaAPIError` (message, code, HTTP-статус).
- `dm_leads` и `site_leads` хранятся раздельно (открытый вопрос ТЗ №5).
- Объявления без активности Meta не возвращает, нулевых строк нет.

## Google Sheets

- Сервисный аккаунт. `GOOGLE_SERVICE_ACCOUNT_JSON` — путь к JSON-ключу или
  содержимое ключа целиком (Railway, где файлов нет). Относительный путь
  считается от папки `jarvis-sheet` (на офисном ПК — `google-key.json` рядом
  со скриптом; в git не попадёт, `*.json` в `.gitignore`).
  Аккаунт должен быть редактором таблицы, иначе
  `SheetsAccessError` («Нет доступа к таблице …»).
- Скрипт трогает только свои листы `meta_daily` и `crm_daily`. Если листа нет,
  он создаётся с заголовками. Существующий лист не меняется, кроме строк данных.
  Остальные листы не удаляются и не меняются.
- Upsert по ключу: `(date, ad_id)` для `meta_daily`, `date` для `crm_daily`.
  Повторный запуск за тот же день обновляет строки на месте.
- Одно чтение листа и один `batch_update` на лист. Полный прогон за день
  вместе с пересборкой листа месяца — 13 запросов к Google API.
- Запись `RAW`: `date` и `ad_id` лежат текстом (иначе Sheets округлит 18-значный
  `ad_id` и переведёт дату в число), числа — числами. В формулах дату
  можно получить через `DATEVALUE`.

## Лист «Сквозная аналитика <Месяц>»

Один лист на календарный месяц. Если его нет, создаётся. Каждый прогон
пересобирает лист целиком из `meta_daily`, `crm_daily` и `ads_manual`.
Ручные правки на самом листе затираются, поэтому править нужно `ads_manual`.

**Лист с таким же названием, заполненный вручную, не стирается**
(признак листа скрипта — скрытая колонка `ad_id` в шапке): скрипт
переименовывает его в «… (вручную)», ничего в нём не меняя, и строит свой
лист рядом. Кодовые слова и статусы с ручного листа (B — название, D — код,
E — статус) подставляются в `ads_manual` для объявлений, которых там ещё
нет; сопоставление по названию без учёта регистра и лишних пробелов. На
таблице заказчика 25.09.2026 совпало 14 из 15 объявлений (15-е в сентябре
не показывалось).

- Колонки: A дата, B–C объявление, D кодовое слово, E статус, F расход,
  G показы, H CPM, I CTR, J заявки с FB, K заявки AmoCRM, L цена заявки,
  M лиды, N CR2, O цена лида, P квал. лиды, **Q встречи** (консультация
  проведена или «в АКТИВном дожиме»), R продажи, S цена квал. лида.
- Строка 1 — «В общем за месяц» (сумма итоговых строк дней, H/I/L/N/O/S —
  формулы от сумм). Строка 2 — шапка. Ниже блоки дней, новые сверху.
- Блок дня: строка на каждое объявление из Meta (по убыванию расхода).
  A (дата) и K–S (CRM) объединены по высоте блока: CRM — одно число на день.
  С кодовыми словами в CRM — группы по слову, см. «Разбивка по кодовому слову».
  Строка «В общем» — итог дня. CPM и CTR итога взвешенные: F/G*1000 и клики/показы.
- CTR из Meta приходит в процентах (0.577 = 0,577%), на лист пишется / 100.
- Скрытые колонки: T — `ad_id`, U — клики (нужны для CTR итогов).
- D (кодовое слово) и E (статус) берутся из `ads_manual` по `ad_id`. Новые
  `ad_id` дописываются туда с пустыми `code_word` и `status`. Существующие
  строки `ads_manual` скрипт не меняет.
- Всё пишется одним `spreadsheets.batchUpdate`, запрос атомарный: при ошибке
  лист остаётся как был.
- Если формулы других листов ссылаются на лист месяца, пересборка
  отказывается (строки сдвигаются, ссылки бы сломались).
- Формулы без разделителей аргументов (`+`, `/`, `IFERROR` с одним
  аргументом): у таблицы локаль ru_RU.

Пошагово — в [OFFICE-PC.md](OFFICE-PC.md). Коротко: код в
`D:\jarvis-sheet` (клон `eliteacademykgf-web/jarvis-sheet`), рядом положить

## Деплой на Railway (запасной вариант)

1. **Сначала на копии таблицы.** Google Sheets → Файл → Создать копию, дать
   сервисному аккаунту (`client_email` из JSON-ключа) роль «Редактор»,
   прогнать локально `python write_to_sheets.py 2026-09-01 <вчера>` и показать
   заказчику. Только потом переключать `SPREADSHEET_ID` на рабочую таблицу.
2. **В рабочей таблице** переименовать ручной лист «Сквозная аналитика
   Сентябрь» (например, в «… (вручную)»): скрипт создаст свой. Кодовые слова
   и статусы объявлений заполнять на листе `ads_manual`.
3. Railway → проект с ботами → **New Service** → GitHub-репозиторий:
   - Settings → **Root Directory**: `jarvis-sheet`;
   - Settings → **Config file path**: `/jarvis-sheet/railway.json` (путь к
     конфигу не следует за Root Directory);
   - Settings → **Watch Paths**: `jarvis-sheet/**`.
   Из `railway.json` подтянутся команда `python run_hourly.py`, крон
   `5 * * * *` и `restartPolicyType: NEVER` (процесс крона должен завершаться).
4. **Variables**: `AMO_DOMAIN`, `AMO_TOKEN`, `META_TOKEN`, `AD_ACCOUNT_ID`,
   `SPREADSHEET_ID`, `GOOGLE_SERVICE_ACCOUNT_JSON` (содержимое JSON-ключа
   целиком), `ALERT_BOT_TOKEN`, `ALERT_CHAT_IDS`. Для уведомлений подойдёт
   любой бот; каждый получатель должен сначала написать ему `/start`.
5. Первый запуск — вручную (Deployments → Run now), проверить лог и лист.
   Историю за прошлые месяцы дозалить локально одной командой
   `python write_to_sheets.py 2026-08-01 2026-08-31`.

### Сроки токенов

- `AMO_TOKEN` (долгосрочный) действует до 26.05.2027 (поле `exp` в токене).
- `META_TOKEN` — токен системного пользователя «Conversions API System User».
  Если истечёт или лишится доступа, придёт уведомление с кодом ошибки Meta.
